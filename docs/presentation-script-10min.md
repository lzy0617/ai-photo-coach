## 第 1 页：封面（0:00—0:25）

各位老师、同学，大家好。我们是郭名扬和刘泽宇，今天展示的项目是 AI Photo Coach，一个基于端云协同的智能人像摄影辅助系统。

它的核心思路可以概括为一句话：让边缘 AI 负责拍摄过程中的即时反馈，让云端视觉大模型负责拍摄之后的深度理解。

## 第 2 页：项目背景（0:25—1:05）

普通用户拍人像时，经常遇到两个问题。第一个问题发生在按下快门之前：人物应该往哪边移动、上方留白是否合适、主体是不是太小，这些问题需要快速反馈。第二个问题发生在拍摄之后：背景是否干扰、光线是否均匀、姿态是否自然，这些又需要更强的语义理解。

在我们的系统中，YOLO 负责检测人物，OpenCV 负责计算位置和亮度；但是光线质量、背景干扰和人物状态，仅靠这些规则很难判断。VLM 能看懂更多画面内容，但处理速度相对更慢。因此我们把实时分析放在香橙派，把拍照后的深入分析交给云端。

## 第 3 页：系统工作流程——香橙派（1:05—1:50）

先看边缘链路。用户通过 Vue 网页打开摄像头或选择照片，浏览器使用 Canvas 将分析副本压缩为最长边 640 像素的 JPEG。请求首先经过香橙派上的 Nginx，再进入 FastAPI 边缘服务。

香橙派使用 Ascend 310B1 和 YOLOv5s OM 模型检测人物，并通过 OpenCV 与构图规则计算位置、上方留白、主体占比和整体亮度。结果随后返回网页，用于绘制人物框、三分线和实时建议。

这条链路不依赖云端，所以即使云端不可用，基本的摄影指导仍然可以继续工作。

## 第 4 页：系统工作流程——云端（1:50—2:30）

云端链路只在用户主动点击“AI 深度分析”时启动。边缘端会把当前照片和最近一次真实的 YOLO、CV 数据一起提交，通过 SSH Tunnel 访问 ModelArts 上的服务。

云端运行在 Ascend 910B3 上，模型是 Qwen3-VL-8B-Instruct。它不再重新估计人物框，而是在已有几何事实的基础上分析场景、光线、背景、姿态和画面表达。

演示时，我们还使用 Cloudflare Quick Tunnel 为网页提供临时 HTTPS 地址，使手机可以直接打开摄像头。

## 第 5 页：拍摄时——实时给出调整建议（2:30—3:20）

[指向截图中的人物框、三分线和实时建议。]

这一页展示的是实时指导界面。网页持续从摄像头抓取低分辨率分析帧，每一轮都严格按照“抓帧、等待边缘分析、更新界面、再进入下一轮”的顺序执行。

YOLO 返回人物框后，前端将检测坐标映射到实际显示画面，并给出人物位置、上方留白、主体占比和亮度信息。系统不会只看单次分数就提示稳定，而是要求连续收到较好的单人人像结果，从而减少检测波动造成的提示跳变。

用户还可以切换前后镜头、调整设备支持的缩放倍率，并控制三分线与人物框是否显示。

## 第 6 页：构图建议如何生成（3:20—4:10）

我们的构图建议直接来自可解释的几何指标。首先根据人物框计算主体横向中心，再计算它与三分线和画面中心的关系；上方留白由人物框顶部除以画面高度得到；主体占比则是人物框面积与整张图面积的比值。

系统允许突出主体的居中人像，不会机械地把所有居中构图都判为错误。最终参考分由位置、留白和主体占比组成，权重分别为百分之四十五、百分之三十和百分之二十五。

这里需要强调，它叫“构图参考分”，不是通用审美分。整体亮度也单独展示，不参与构图分，因为明暗本身可能是摄影者主动选择的表达方式。

## 第 7 页：拍照后——Qwen3-VL 深入分析（4:10—5:00）

[指向左侧深度分析截图，再指向右侧输入和输出。]

传统几何规则能够告诉我们人物在哪里，但无法可靠判断背景中的出口标志是否抢眼、面部受光是否均匀、姿态是否自然。因此深度分析同时接收图像和 CV metrics。

我们在提示词中明确规定：检测框、位置、占比和留白属于边缘端提供的几何事实，大模型只负责补充视觉语义。模型输出被约束为结构化 JSON，包括场景、光线、背景、姿态、画面表达以及最多三条有原因的可执行建议。

这样做不是让 VLM 替代 YOLO，而是让两种能力各自处理更擅长的问题。

## 第 8 页：关键代码 A——YOLO 人物框如何回到原图（5:00—5:40）

YOLO 得到的检测框位于补边后的 640×640 画面中，不能直接画到手机原图上。因此代码先从模型坐标中减去 `pad_x` 和 `pad_y`，去掉 letterbox 补边，再除以 `scale`，还原为原图像素坐标。

还原后，坐标会被限制在原图范围内，避免检测框超出图片边界。最后再除以原图宽高，得到零到一之间的归一化坐标，前端就可以按百分比绘制人物框。

这一步保证了不同分辨率、不同横竖比例的照片在网页上缩放显示时，人物框仍然能够与人物对齐。

## 第 9 页：关键代码 B——如何把人物框变成构图建议（5:40—6:20）

这段代码对应刚才的几何计算。所有坐标都会除以画面宽高，转换为归一化比例，因此不同手机分辨率和横竖屏画面可以使用同一套阈值。

人物中心用于分析横向位置，人物框面积用于分析主体占比，`y1` 与画面高度的比值用于分析上方留白。三个维度分别评分后，再按照四十五、三十、二十五的权重组合。

这种规则的优势是结果可追溯：每一条“向左移动”或“扩大取景”的建议，都能对应到一个明确的几何关系。

## 第 10 页：关键代码 C——如何把照片和构图数据交给 VLM（6:20—7:00）

这一部分展示端云之间的实际数据协议。边缘端通过同一个 multipart 请求发送 JPEG 图像和序列化后的 `cv_metrics`；云端再把图片与包含指标、任务说明和 JSON 结构约束的提示词共同交给 Qwen3-VL。

模型生成之后，云端先解析 JSON，边缘端还会兼容常见包装结构并统一字段。如果模型超时、网络断开或者输出格式不合法，系统不会清空已有结果，而是保留 YOLO、CV 分析并提示用户稍后重试。

这使云端能力成为增强项，而不是整个拍摄流程的单点故障。

## 第 12 页：遇到的问题与解决办法（8:15—9:00）

开发过程中，我们主要解决了五类工程问题。

第一，大图上传慢，所以在浏览器生成 640 像素分析副本，同时保留原图用于预览和保存。第二，实时请求容易堆积，因此改用串行请求和互斥状态。第三，纯规则建议容易显得机械，所以把它限定为构图参考，并让 VLM 补充语义。

第四，云端较慢或失败时，系统自动降级，YOLO 仍可使用。第五，手机浏览器要求安全上下文，所以使用 Cloudflare Quick Tunnel 提供临时 HTTPS 入口。

这些优化共同保证了：增强能力出现故障时，基本拍摄流程仍然可用。

## 第 13 页：项目总结与下一步（9:00—9:45）

目前项目已经完成实时指导、照片诊断、边缘 YOLO、云端 Qwen3-VL、端云 SSH 连接和手机演示网页，验证了端云协同方案的完整可行性。

当前系统主要面向单人人像，构图分只反映几何关系，大模型建议也具有生成不确定性。下一步可以将临时入口升级为固定域名和访问控制，把同步深度分析改成异步任务，并加入更丰富的构图与面部光线规则。

同时，我们希望使用真实拍摄样本建立评测集，从建议准确性、响应延迟和用户可执行性三个方面进一步评价系统。简单概括就是：香橙派负责实时分析和反馈，云端模型负责给出更详细的建议。

## 答辩前代码阅读重点

不需要平均阅读整个仓库。先把下面四条主线弄懂，已经足够覆盖幻灯片和大部分现场提问。

### 第一优先级：一定要能讲清楚

1. `edge-backend/app.py`
   - 重点看 `analyze_fast()`：一张图片如何依次经过 YOLO、构图分析和亮度分析，再组成返回给前端的数据。
   - 再看 `deep_analyze()`：为什么必须同时提交图片和 metrics，以及云端失败后如何保留快速分析结果。
   - 看完后要能回答：“两个 API 分别做什么，为什么要拆开？”

2. `edge-backend/composition.py`
   - 重点看 `analyze_composition()`：人物中心、人物面积占比、上方留白如何计算，三项分数如何组合。
   - 注意“大面积单人人像允许居中”的特殊判断，以及多人时如何选择主要人物。
   - 看完后要能回答：“构图分怎么算，为什么它不等于照片的审美分？”

3. `frontend/src/views/LiveGuide.vue`
   - 重点看 `loop()`、`start()`、`takePhoto()` 和 `analyzeDeep()`。
   - 理解为什么上一帧分析完成后才发送下一帧，以及暂停、切镜头、缩放时为什么要丢弃旧结果。
   - 看完后要能回答：“为什么不用 `setInterval`，请求如何避免越积越多？”

4. `edge-backend/services/vlm_client.py` 与 `cloud-vlm/app.py`
   - 在 `vlm_client.py` 中看 `VLMClient.analyze()`：照片和构图数据如何通过 multipart 请求送到云端，以及超时、连接失败和错误 JSON 如何处理。
   - 在 `cloud-vlm/app.py` 中看 `build_prompt()`、`QwenVLService.analyze()` 和 `/analyze`：提示词如何划分 YOLO 与 VLM 的职责，模型如何生成并解析 JSON，为什么使用推理锁。
   - 看完后要能回答：“为什么 VLM 不重新计算人物框？模型输出不合法怎么办？”

### 第二优先级：演示前最好看一遍

- `frontend/src/api/photography.js`：前端怎样调用两个 API，快速分析锁和深度分析锁分别解决什么问题。
- `frontend/src/composables/useCamera.js`：HTTPS 要求、摄像头权限、640px 分析帧和高质量照片为什么分开生成。
- `edge-backend/detector.py`：重点理解 letterbox、Ascend NPU 推理和坐标映射；不需要背 ACLLite 的每个调用。
- `frontend/src/utils/liveStability.js`：为什么需要连续的合格结果，才提示“当前构图较稳定”。
- `frontend/src/utils/overlay.js` 与 `CompositionOverlay.vue`：检测框坐标如何映射到页面，以及标签为什么不会被人物框宽度裁掉。

### 可以略读的部分

- 普通卡片组件、图标组件和大部分 CSS：知道它们负责展示即可，不必逐行解释。
- ACLLite 底层实现和 YOLO 模型转换细节：除非答辩明确要求模型部署过程，否则理解输入、推理和输出坐标这三步即可。
- 测试文件：了解项目对深度分析降级和返回格式做过测试，不需要记住每个断言。

最有效的准备方法不是背代码，而是沿着一张照片走一遍：浏览器抓帧 → `/api/analyze-fast` → YOLO 人物框 → 构图规则 → 页面显示 → 用户点击深度分析 → `/api/deep-analyze` → SSH 隧道 → 云端 `/analyze` → Qwen3-VL JSON → 页面展示。只要能不看稿讲清这条链路，展示中的技术部分就基本稳了。
